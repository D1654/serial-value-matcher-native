## 1. Project Vision

SerialValueMatcher Native will keep its validated lightweight Win32 native release experience while creating a maintainable architecture runway for future features. The work prioritizes UI stability, main-window boundary cleanup, serial/Modbus/storage consistency, evidence/report foundations, and release-grade verification before adding new protocol runtime features.

## 2. Architecture Overview

The target architecture is a layered native design: `NativeMainWindow` remains the Win32 shell for messages, lifetime, and HWND ownership; feature state and commands move into controllers/services; protocol, transport, matching, report, and storage behavior live behind testable core boundaries. Production layout must consume `NativeLayoutModel`, backend work must use queued/evented paths, and release governance must validate the exact GitHub Actions Windows exe/zip artifact.

```text
Win32 Message Loop
        |
        v
+--------------------+
| NativeMainWindow   |  message/lifetime/HWND shell
+---------+----------+
          |
          v
+--------------------+      +----------------------+
| Feature Controllers|----->| NativeLayoutModel    |
| serial/send/log/...|      | Layout Transactions  |
+---------+----------+      +----------------------+
          |
          v
+--------------------+      +----------------------+
| Core Services      |----->| SessionStore Port    |
| protocol/modbus/   |      | file backend now     |
| matcher/report     |      | SQLite gate later    |
+---------+----------+      +----------------------+
          |
          v
+--------------------+
| Transport Port     |
| Serial now         |
| TCP reserved later |
+--------------------+
```

## 3. Tech Stack

| Component | Choice | Rationale |
|-----------|--------|-----------|
| Language | C++20 | Matches the current codebase and keeps native performance and package size under control. |
| Framework | Win32 API | Current user-validated delivery is a small Windows native exe; no Qt/Electron/WebView runtime enters native release. |
| Database | Compatible native file storage; SQLite decision gate | File backend stays compatible now; SQLite is only considered later for indexed cross-session/evidence queries. |
| Testing | CTest/native tests; optional GoogleTest only as dev/CI | Existing test fleet is large and useful; richer test framework is allowed only if it stays out of release artifacts. |
| Build Tool | CMake + GitHub Actions | Existing build/test/package workflows already form the right backbone and should be hardened rather than replaced. |
| Deployment | GitHub Actions Windows native exe/zip | The final acceptance target is the packaged release artifact, with logs, screenshots, package audit, docs consistency, and hash evidence. |

## 5. Success Criteria

- [ ] The GitHub Actions Windows native exe/zip remains the final acceptance target and passes package, docs, self-test, UI perf, and dependency gates.
- [ ] Production UI uses tested layout/model/transaction paths and avoids tab blanks, hidden controls, resize collapse, and visible flicker regressions.
- [ ] `NativeMainWindow` no longer owns expanding business logic; serial/send/log/modbus/analysis/preferences behavior has explicit controller/service boundaries.
- [ ] Serial writes do not block the UI thread and have bounded queue behavior, timeout/cancel/failure events, and reproducible fake/loopback evidence.
- [ ] Modbus scan/read/match behavior uses a single executor/transaction model for timeout, retry, exception, and result handling.
- [ ] Native storage has schema versioning and recoverable file-commit/orphan handling before evidence package expansion.
- [ ] New extension foundations, including evidence bundle and command sequence, remain local, explicit, and safe; no TCP UI/runtime is implemented.
- [ ] Release metadata, README, docs, package summary, and release notes are kept consistent by checks.

## 6. Risk Register

| # | Risk Description | Probability | Impact | Mitigation Strategy |
|---|------------------|-------------|--------|---------------------|
| 1 | `NativeMainWindow` cleanup becomes a broad rewrite and breaks validated UI | Medium | High | Extract seams in small tasks, preserve screenshots/UI perf/CTest after each task. |
| 2 | Architecture creates abstract layers without reducing real complexity | Medium | High | Tie every boundary to a known hot spot: layout, serial, Modbus, storage, evidence, or release drift. |
| 3 | Async write queue introduces ordering/cancel/timeout races | Medium | High | Use fake transport, loopback evidence, state tests, and explicit event states. |
| 4 | Modbus executor unification changes behavior | Medium | High | Lock request/response/exception/CRC/timeout behavior with focused tests before replacing UI paths. |
| 5 | Native file storage recovery is insufficient for future evidence packages | Medium | High | Implement schema/commit/recovery before evidence expansion and add fault-injection tests. |
| 6 | UI performance remains subjective | Medium | Medium-High | Use current `--ui-perf-test` and screenshot artifacts as baseline-derived thresholds. |
| 7 | Serial PTY stress is mistaken as fully CI-blocking | Medium | Medium-High | Keep current PTY loopback as local pre-release evidence until a CI-capable substitute is implemented. |
| 8 | Dependency/size governance drifts because 10MB is treated as a target | Low-Medium | Medium | Treat 10MB as an absolute red line; require necessity, package delta, and benefit for every dependency. |
| 9 | Future TCP/multi-protocol requirements leak into this phase | Medium | High | Reserve interfaces only; no TCP UI/runtime in this plan. Future TCP requires a separate gate. |
| 10 | Docs, release notes, package metadata, and screenshots drift again | Medium | Medium | Harden docs/package consistency checks and version metadata tasks. |
