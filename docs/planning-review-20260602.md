## 1. 总体结论

当前路线重排的方向是正确的：

- 没有继续把 Native 做成普通串口助手；
- 已经把下一步从“接收区显示增强”改为“Modbus RTU 只读扫描内核”；
- 重新回到了 SerialValueMatcher 的核心业务主线：目标值、扫描、候选、证据、导出。

但如果问“是否可以真的覆盖我们的需求”，当前规划还需要加固。主要缺口有三类：

1. **事实持久化不足**：Task 05 原计划只做“最小持久化设计检查”，这不足以支撑后续候选、证据、历史和导出。
2. **真实串口集成缝不足**：Task 05 原计划以 fake executor 为主，但没有明确真实 `SerialPortService` 如何接入扫描执行器，容易做出测试能过、真实串口难接的内核。
3. **UI 纵向闭环太晚**：完整 UI 可以放到 Task 08，但应该更早规划“薄 UI 闭环”或至少保留入口，否则业务需求会长期停留在库层。

因此结论是：

> 规划方向正确，但需要修订 Task 05，并补充后续任务边界，才能更可靠地覆盖最初业务/功能/UI需求。

## 3. 主要发现

### F1. Task 05 只做“持久化设计检查”不够

原计划 T05F 写的是：

> 本任务可以先不完整落 SQLite 表，但必须明确后续持久化结构。

这与最初需求存在冲突。旧架构强调 SQLite 是事实来源，候选、证据、历史、导出都要能从数据库重建。如果 Task 05 只产出内存观测，后续 Task 06/07 很容易把候选逻辑绑定到临时对象，最后再补数据库会返工。

建议：

- Task 05 应至少落地最小扫描会话和寄存器观测持久化；
- 不一定做完整历史页面，但必须有 repository / tests；
- `raw_io_events` 与扫描观测的关联关系要明确。

### F2. fake executor 必要，但不能没有真实传输契约

fake executor 对自动化测试很重要，但真实业务依赖串口。当前规划没有明确：

- 扫描执行器如何调用真实串口；
- 如何等待响应；
- 如何处理超时；
- 如何避免 UI 线程阻塞；
- 如何把请求/响应都进入 `CaptureBus` / SQLite。

建议：

- 新增抽象传输接口，例如 `IModbusRtuTransport` 或等价 Qt 类；
- fake transport 和 real serial adapter 都实现同一契约；
- Task 05 不一定做真实硬件验证，但必须保留真实串口接入点。

### F3. UI 完整页面可以后置，但“业务入口”不能太晚

完整扫描 UI 放到 Task 08 是合理的，因为先做核心和测试更稳。但如果 Task 05/06/07 都只做库层，用户长期看不到业务进展，也无法验证中文工作流。

建议：

- Task 05 仍保持 UI 无关；
- Task 06 或 Task 07 后必须插入一个“薄 UI 纵向切片”；
- 最小 UI 只需要：扫描范围、目标值、开始扫描、候选表、证据摘要；
- 不要一开始复刻旧 WPF 10 页完整导航。

### F4. 私有协议被后置是合理的，但路线要防止 Modbus 专用化

Native 的核心数据流应该是：

```text
QSerialPort -> SerialPortService -> CaptureBus -> SQLite/UI/Analysis Extension
```

Modbus 扫描只是其中一个消费者/工作流。如果 Task 05 把扫描结果和串口服务绑死，后续私有协议规则会困难。

建议：

- Modbus codec 独立；
- 扫描执行器消费 transport，不直接控制 UI；
- 原始 RX/TX 继续统一进 `CaptureBus`；
- `RawIoEvent` 保持协议无关。

### F5. 安全验收需要更具体

当前规划提到只读安全，但测试项还不够完整。

建议至少测试：

- slave id `0` 拒绝；
- 非 FC03/FC04 拒绝；
- quantity 超限拒绝；
- 地址范围溢出拒绝；
- 请求数量估算；
- 大范围扫描标记风险等级；
- 异常响应可记录但不误判成功。

### F6. 用户最初的 UI/体验要求还应进入路线约束

用户明确追求性能和 UI 体验，且要求中文母语视角。路线里应明确：

- 每个新业务页都要中文状态/空状态/错误说明；
- 不裸露英文枚举；
- 不一次性大改界面；
- 每个页面或纵向切片都要能构建、能测试、能启动。

## 4. 建议修订

### R1. 修订 Task 05

把 Task 05 从：

```text
Modbus RTU 只读扫描内核 + 持久化设计检查
```

修订为：

```text
Modbus RTU 只读扫描内核 + 最小持久化 + 真实传输契约
```

新增/调整子任务：

- T05F：最小扫描持久化落地，而不是只做设计；
- T05G：真实串口传输契约与 adapter 边界；
- 文档中明确 Task 06 可以直接读取扫描事实生成候选。

### R2. 调整后续路线

建议路线改为：

```text
Task 05：Modbus RTU 只读扫描内核 + 最小持久化 + 传输契约
Task 06：目标值匹配与候选生成
Task 07：候选证据、多样本复读与人工决策
Task 08：Modbus 扫描薄 UI 纵向闭环
Task 09：历史回放与导出报告
Task 10：串口诊断增强、搜索过滤、宏与日志回放
Task 11：私有协议规则与字段分析第一批
Task 12：Windows 打包、实机验证与性能基线
```

### R3. 增加阶段性验收门

每个阶段不能只看 `ctest`，还要看是否覆盖业务闭环：

- Task 05：能从 fake device 扫到寄存器事实并落库；
- Task 06：能从寄存器事实生成候选；
- Task 07：能通过多样本把候选置信度拉开；
- Task 08：普通用户能在 UI 上完成一次最小扫描匹配；
- Task 09：历史和报告能复盘这个最小闭环。

## 5. 最终审查判断

当前规划：**部分覆盖需求，方向正确，但还不能说已经可靠覆盖全部需求。**

必须修正后才能进入执行：

1. Task 05 增加最小持久化落地；
2. Task 05 增加真实传输契约；
3. 后续路线插入薄 UI 纵向闭环；
4. 每阶段验收从“功能完成”升级为“业务事实可复盘”。

修正后，路线可以覆盖最初业务需求，并且比直接复刻旧 WPF 更稳。
