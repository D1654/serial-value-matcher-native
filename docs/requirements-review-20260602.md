# 需求回视与 Native 路线重排

日期：2026-06-02

## 1. 为什么要回视

Task 03 / Task 04 已经把 Native 工程推进到“可继续扩展的串口调试底座”：串口枚举、连接、完整参数、Profile、自动重连、文本/HEX 发送、RX/TX 事件、SQLite、发送历史和中文错误诊断都已落地。

但 SerialValueMatcher 的最初目标不是“再做一个普通串口助手”。如果后续只继续补搜索、过滤、宏、显示格式，很容易偏离核心业务。因此在继续新任务前，需要重新对齐：

- 业务需求：用户真正想解决什么问题；
- 功能需求：哪些能力必须能跑通、能保存、能验证；
- UI 需求：中文现场用户应该按什么流程完成任务。

## 3. 核心业务需求

### B1. 找到“现场真实值”对应的寄存器地址或协议字段

用户关心的不是单纯收发 HEX，而是：

1. 已知现场某个真实业务值，例如温度、压力、流量、重量、转速；
2. 软件通过只读通信采集一批数据；
3. 软件推测哪些寄存器地址或私有协议字段可能对应这个真实值；
4. 用户通过多次目标值变化和重复读取验证候选；
5. 最终留下可解释、可导出的证据。

### B2. 支持标准 Modbus RTU 与非标准私有协议

第一条业务主线是 Modbus RTU 地址匹配：

```text
连接配置 -> 扫描设置 -> 候选结果 -> 目标样本 -> 候选证据 -> 历史回放 / 导出报告
```

第二条业务主线是私有协议诊断：

```text
私有协议规则 -> 串口诊断 -> 协议验证结果 -> 导出验证报告
```

Native 第一阶段可以先做成熟串口调试底座，但后续必须回到这两条业务主线。

### B3. 结果必须能复盘、能导出、能交付

SQLite 是事实来源。重要事实不能只存在 UI 临时状态里，至少包括：

- 串口配置；
- 扫描会话；
- 目标样本；
- 原始通信记录；
- 寄存器观测；
- 候选、评分、证据；
- 人工确认 / 排除；
- 私有协议规则与验证记录；
- 导出记录。

### B4. 安全是产品功能，不是附加说明

现场串口设备可能接生产设备。软件必须坚持：

- 常规扫描只使用 FC03 / FC04 只读功能码；
- 拒绝广播从站 ID `0`；
- 大范围扫描前提示请求次数和耗时；
- 手动 TX 属于危险操作，默认关闭；
- 单次候选不能直接等价为结论，必须鼓励多样本验证。

### B5. Native 主线必须轻量、中文、稳定

Native 的意义不是重写旧 UI，而是：

- 摆脱 .NET Desktop Runtime 依赖；
- Windows 原生轻量交付；
- 中文现场用户第一视角；
- 低资源占用；
- 长时间运行稳定；
- 可扩展到 Analysis Extension。

## 4. 功能需求分层

### 第一层：串口调试底座

状态：Task 03 / Task 04 已完成主要基础。

已覆盖：

- 串口枚举、刷新、连接、断开；
- 完整串口参数；
- Profile 保存/恢复；
- 自动重连骨架；
- 文本/HEX 发送；
- 行尾设置；
- RX/TX 事件进入 `CaptureBus`；
- SQLite 保存原始通信事件；
- 发送历史；
- 中文错误诊断；
- 暂停滚动、清空接收区。

仍可增强但不是最高优先级：

- 搜索/过滤；
- 宏/常用命令；
- 原始日志导入/回放；
- 独立 TxRx 监视窗口；
- 长时间运行性能基线。

### 第二层：Modbus RTU 只读扫描与匹配

这是下一阶段应优先推进的业务主线。

需要补齐：

- Modbus RTU 请求/响应编解码；
- CRC16/MODBUS；
- FC03 / FC04 只读请求；
- 地址范围、块大小、请求间隔、安全等级；
- 扫描会话与寄存器观测持久化；
- 目标值输入；
- 候选生成：数据类型、字节序、倍率、容差；
- 候选评分与证据；
- 多目标样本与重复读取验证；
- 人工确认 / 排除；
- 历史回放与导出报告。

### 第三层：私有协议规则与字段分析

应在串口底座和 Modbus 只读扫描稳定后接入。

需要补齐：

- 分帧规则：固定长度、帧头、长度字段、帧尾；
- Checksum / CRC；
- 字段解码：UInt16/UInt32 BE/LE、PackedBCD、Gray16BE、BitFlags8；
- 草稿 HEX 离线测试；
- 保存规则；
- 应用规则到 RX/TX 日志；
- 候选字段评分；
- 导出 Markdown / CSV 证据。

## 5. UI 需求回视

### UI1. 主流程必须面向现场用户

推荐流程应保持：

```text
连接设备 -> 配置扫描 -> 输入目标值 -> 生成候选 -> 追加样本 -> 复读验证 -> 查看证据 -> 导出/回放
```

UI 不应只展示技术控件，而要告诉用户：

- 现在应该做什么；
- 为什么按钮不可用；
- 下一步去哪；
- 当前结果是否足以作为结论；
- 风险在哪里。

### UI2. 中文优先，避免英文枚举裸露

中文用户可见区域应优先显示中文解释，例如：

- `FC03 Holding Registers` 应显示为“FC03 保持寄存器（只读）”；
- `EvenParity` 应显示为“偶校验”；
- 错误提示应解释“串口被占用 / 驱动异常 / 参数错误 / 设备无响应”。

### UI3. 小步演进，避免一次性大改

旧项目曾出现全界面响应式大改后无法启动的严重回归。Native 后续 UI 应坚持：

- 每次只改一个页面或一个业务闭环；
- 每步都有构建和测试；
- 不用大规模重排掩盖业务逻辑不足；
- 先核心流程，后视觉 polish。

### UI4. Native 当前 UI 与目标页面差距

旧 WPF 项目已有页面概念：

1. 连接配置；
2. 扫描设置；
3. 目标样本；
4. 候选结果；
5. 候选证据；
6. 历史回放；
7. 导出报告；
8. 私有协议规则；
9. 串口诊断；
10. 日志与错误。

Native 当前仍是单窗口基础工作台。下一步不必立即复刻完整导航，但需要开始引入业务区块，至少先让 Modbus 扫描主线有明确入口。

## 7. 路线重排结论

之前直觉上想把下一步排成“接收区显示增强”，但需求回视后应调整：

- 搜索、过滤、宏、显示增强仍重要；
- 但它们属于串口助手体验增强；
- 当前更应该先回到 SerialValueMatcher 的业务主线：只读扫描、目标值、候选、证据。

因此下一步应改为：

```text
Task 05：Modbus RTU 只读扫描内核 + 最小持久化 + 传输契约
Task 06：目标值匹配与候选生成
Task 07：候选证据、多样本复读与人工决策
Task 08：Modbus 扫描薄 UI 纵向闭环
Task 09：历史回放与导出报告
Task 10：串口诊断显示增强、搜索过滤、宏与回放
Task 11：私有协议规则与字段分析第一批
Task 12：Windows 打包、实机验证与性能基线
```

这个顺序的原则是：

1. 先让业务事实可采集；
2. 再让候选可生成；
3. 再让证据可确认；
4. 再增强 UI 和串口助手体验；
5. 最后进入私有协议 Analysis Extension。
